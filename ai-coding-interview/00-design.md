# 出题原则：1 小时里真正能考到 Harness AI

## 这轮要考什么

Harness AI 不是「会不会打开 Cursor」，而是候选人把模型当成同事时的工作方式：

1. **任务拆解**：60 分钟里先保 P0，还是一上来让 AI 重写整个项目。
2. **上下文质量**：prompt 是否包含验收标准、约束、相关文件，还是一句「帮我修一下」。
3. **验证闭环**：会不会跑测试、打开页面点一下、对照任务书勾验收；还是看 AI 说 done 就结束。
4. **纠偏**：AI 修错、测不过、或过度设计时，是读代码定位，还是无限「再试一次」。
5. **判断力**：会不会接受一堆用不上的抽象、新框架、和现有代码风格冲突的补丁。
6. **模糊需求**：筛选「可叠加」是 AND 还是 OR、URL 要不要 `replaceState`——会问、会写进注释/README，还是默默猜。

代码对不对只是结果；**过程**才是这轮的区分度。

## 1 小时题必须满足的约束

- **零启动成本**：clone 后不用装框架、不用配数据库。环境问题会把面试变成运维。
- **不是绿场**：必须有一份「别人写的」小代码。绿场题 AI 会生成一套通用 CRUD，看不出她会不会读现有约定。
- **有失败的测试当反馈**：候选人（和 AI）能 `npm test` 知道修没修好。没有反馈的题，只会得到「看起来能跑」。
- **有 AI 常错的点**：XSS、错误的 filter 语义、URL 状态不同步、删除后 ID 冲突。这些点能区分「盲信生成」和「有审查」。
- **有一处故意写含糊的需求**：逼她提问或自己写清决策。全是封闭需求时，考不到沟通。
- **工作量可切割**：P0 / P1 / P2。实习生 1 小时很少做完，必须能按完成度打分。

## 不要出的题

| 题型 | 为什么不适合 |
| --- | --- |
| LeetCode / 手写快排 | 模型几乎秒杀；看不出 harness，只看出没开工具。 |
| 「用 AI 从零做个 Twitter」 | 1 小时只能做出壳；区分度在 UI 品味，不在工程判断。 |
| 纯 prompt 笔试（不许跑代码） | Harness 的核心是 **跑、看、改**，不是写作文。 |
| 需要付费 API / 复杂权限的题 | 面试当场卡在 key 和环境。 |
| 和岗位无关的深度算法/编译器 | 实习生面试应贴近日常：读代码、修 bug、加小功能、补测试。 |
| 把答案写在注释里（`// BUG: 大小写`） | 模型会 grep 到，题就废了。 |

## 推荐题型（本目录已给一版）

**「有缺陷的迷你 Issue Board」**：vanilla JS + Node 内置测试。

| 层级 | 内容 | 考什么 |
| --- | --- | --- |
| P0 | 搜索、状态筛选、XSS | 读现有代码、跑测试、安全意识 |
| P1 | labels + URL 同步筛选 | 在约束下加功能、处理模糊需求 |
| P2 | 空标题校验、删除后 ID 唯一、补测试 | 时间管理、测试习惯 |

这题对 AI 来说「能做完，但不容易一次做对」：模型常漏 XSS、把 `status=all` 修成另一种错、URL 只写不读或用错 `pushState`。

## 备选（觉得 Issue Board 太前端时）

1. **修一个会算错的优惠券结算模块**（纯函数 + 单测）：更偏逻辑，仍然要验证和防过度设计。
2. **给一份 200 行脚本加 `--dry-run` 和错误处理**：更偏工具/后端实习生。
3. **Review 一份 AI 已经提交的 PR，找出 3 个问题并改掉**：如果只想考审查能力，可以把「生成」拿掉，只留 harness 的后半段。

正式面试只用其中一题，不要三题并行。

## 面试形式建议

- **屏幕共享 + 出声思考**。不看操作就只剩最终 diff，Harness 几乎无法评分。
- **允许任何模型**。限制模型会变成「谁会员更贵」，不是谁更会用。
- **不要在旁边催 prompt 怎么写**。卡住 3 分钟再给一个中性提示：「你现在的验收标准是什么？」
- **结束时问三句**：
  1. AI 哪一步是对的，哪一步你不该原样收下？
  2. 你怎么知道做完了？
  3. 还剩什么没做，为什么先做手上这些？
